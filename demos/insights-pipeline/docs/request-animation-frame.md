# requestAnimationFrame，这个项目的脉搏

今天上午发生了一件有点诡异的事：序章的文字动画播到一半卡住了——标题字符全部亮起，但下面的正文和按住按钮一直停在透明状态，十几秒都不动。我当时以为是自己改坏了代码，查了半天才发现：页面标签页在后台。浏览器把整个动画冻结了，切回前台的那一瞬间，动画立刻接着播完，行云流水。

罪魁祸首就是这篇文章的主角：requestAnimationFrame，简称 **rAF**。你从起手这个项目开始就不断看到这个词，它确实是这个项目的骨骼。这篇文章把它一次讲透。

## 一句话：一个「下一帧开始前叫我」的函数

浏览器把画面一帧一帧画出来，你的屏幕如果刷新率是 60Hz，那么每秒会画出 60 帧，也就是大约每 16.7 毫秒一帧。`requestAnimationFrame(callback)` 就是告诉浏览器：

> 下一次画帧之前，先叫我一声。

浏览器收到请求后，会在**这一帧开始渲染前**执行你的回调。你在回调里更新画面（移动粒子、改透明度、渲染 3D 场景），浏览器紧接着就把这帧画出来。如此循环，动画就流畅地跑起来了。

它的名字拆开看就是这个意思：request（请求）+ animation（动画）+ frame（帧）——请求一帧动画。

## 为什么不用 setInterval？为什么它值得被单独立成一个 API？

你可能会想：用 `setInterval(fn, 16)` 不也是每 16 毫秒跑一次吗？能，但有两个致命问题：

**第一，setInterval 不知道屏幕什么时候刷新。** 假设它恰好卡在两次刷新之间执行，你更新完画面，但这一帧已经画完了，你的更新要等下一帧才显示——那一次更新就白做了，画面会显得「抖」。反过来，如果 setInterval 比刷新快，一帧内会被更新多次，浪费。rAF 永远卡在刷新前执行，保证「你画了，这一帧就能被看到」。

**第二，rAF 会自动省电。** 页面在后台、看不见的时候，浏览器直接不调用 rAF 回调——没人看，何必费电画帧？Chrome 从 2011 年起就是这个行为，MDN 官方文档写得直白：「为了提高性能和电池寿命，大多数浏览器会暂停后台标签页中运行的 requestAnimationFrame 调用」。而 setInterval 在后台虽然会被节流到每秒一次，但该跑还是跑。

所以 rAF 是浏览器为动画专门设计的心跳，setInterval 是给「定时干活」用的，两码事。

## 三条规矩

rAF 有几个容易踩的规矩，项目代码里都有对应：

1. **它是一次性的，不是循环。** 每次回调执行完，rAF 就结束了。想继续动画，必须在回调里再调用一次 `requestAnimationFrame`。忘了这件事，动画跑一帧就死。scroll.js 的主循环就是这种「自续」结构：`tick` 函数末尾再请求一次自己。

2. **回调的第一个参数是时间戳。** 浏览器会把「本次回调的时刻」作为参数传给你。用它算进度，别自己数「我跑了几帧」——因为帧率不稳定，数帧会在 120Hz 屏幕上跑成两倍速。项目里 hold.js 的按住进度就是这么算的：`(现在时刻 - 按下时刻) / 按住时长`。

3. **频率跟着屏幕走。** 60Hz 屏幕一秒约 60 次，144Hz 电竞屏约 144 次。代码不能假设「每帧固定过 16.7 毫秒」，所以项目里所有动画都按**实际经过的时间**（dt）推进，而不是「每帧前进固定值」——这叫帧率无关，在 60Hz 和 144Hz 上动画速度一致。

## 后台冻结：这不是 bug，是设计

回到今天上午的事。浏览器为了省电，对后台标签页不调用 rAF。Chrome 的开发者博客明确记载：**页面在后台时，Chrome 不会调用 rAF，这个行为自 2011 年起就有**。而且有一个细节值得知道：页面在后台的标签页停留 5~10 秒后，就算降级也只会拿到约 8fps；切回前台立即恢复满帧。

这带来一个推论：**凡是用 rAF 驱动的动画，都会在后台冻结。** 本项目所有的动画几乎全挂在 rAF 上——不光是 gsap 的动画，还有粒子河的流动、滚动平滑、按住进度环。所以这个 demo 在后台标签页里会整个「时间停止」，切回来瞬间恢复，像什么都没发生一样。

这其实是个省电的恩赐，只是调试的时候容易让人误以为是代码坏了。今天上午就是这么误会的。

## 和 gsap 是什么关系：gsap 是一个披着 rAF 的引擎

gsap（GreenSock Animation Platform）是这个项目用的动画库，S1 的打字、星云的展开、黑场淡入都是它做的。它的核心机制是 `gsap.ticker`——官方文档称之为「引擎的心跳」：一个 rAF 循环，每次帧回调时推进全局时间轴，把所有正在播的动画统一推进一帧。

换句话说，**gsap 底层就是 rAF**。你在代码里写的每一个 `gsap.to(...)`，最终都是挂在这个 rAF 心跳上的一笔账。所以：

- gsap 动画和屏幕刷新天然同步，不会抖；
- 后台标签页 rAF 冻结 → gsap 心跳停跳 → 所有 gsap 动画冻结（今天上午序章卡住就是这个链条）；
- gsap 还内置了一个叫 `lagSmoothing` 的机制：如果 CPU 忙，两帧之间隔了很久，它会假装只过了 33 毫秒，防止动画「跳一大步」。对用户来说就是：卡顿的时候动画会慢一点点，但不会突然瞬移。

## 和谷歌开发者工具 MCP 是什么关系：rAF 是你的探针

这里有个容易混淆的点：rAF 是浏览器页面的 API，chrome-devtools MCP 本身不提供什么「rAF 工具」。关系在于——**MCP 的 evaluate_script 能让你在页面里跑任意 JavaScript，于是你可以自己写一个临时 rAF 循环当探针**。

今天上午我判定「rAF 活着」用的就是这招：往页面里塞一段代码，自己开一个 rAF 计数器，数一秒钟内回调跑了多少次。结果 166 次——说明页面在前台、渲染循环健康。如果数出来是 0，就说明要么循环死了（代码抛异常），要么页面在后台。这就是「探针」的含义：不是 MCP 提供的现成工具，而是借助 MCP 的任意代码执行能力，用 rAF 当温度计量一量页面的心跳。

顺带一提，如果你打开 DevTools 的 Performance 面板录制一段，能看到每一帧的耗时分布——那是浏览器自己用 rAF 时间戳画的帧图，和探针看到的是同一件事。

## 这个项目里的 rAF 地图

数了一下，这个 demo 里有五处 rAF 在各自岗位上班：

**scroll.js —— 主循环（整个项目的心跳）。** 滚动输入的轮子、键盘、触屏，全都汇成一个目标位置；rAF 循环每帧把当前位置向目标平滑逼近（lerp），然后把「当前值、目标值、经过时间」喂给时间轴，最后触发一次 3D 渲染。整条流水线就靠这一个循环活着，所以 main.js 注释里写「场景不自持 rAF，单循环驱动」——粒子、星云、黑场，全都由它统一叫醒。

**gsap.ticker —— 节拍动画。** 每个场景的入场节拍（打字、命中闪、星云展开、黑场三段式）都是 gsap 时间线，挂在 gsap 自己的 rAF 心跳上，跟 scroll 的主循环并存互不干扰。

**hold.js —— 按住推进。** 按住按钮时，一个独立的小 rAF 循环按真实经过的时间推进进度环，松手就停。

**prologue.js —— 视差。** 序章背景随鼠标微移的视差，用 rAF 做平滑跟随。但它有个聪明的细节：只有鼠标移动时才启动这个 rAF，不动就停——跟浏览器后台冻结是同一个省电哲学。

**timeline.js —— 时间轴时钟。** 它不自持 rAF（这是设计），而是被 scroll 的主循环每帧喂一次 `t`（累计时间）。项目特意把「时间源」收敛成唯一一个，避免两个循环各走各的钟导致动画对不上。

## 三条用血泪换来的经验

这个项目在 rAF 上踩过的坑，写下来给你：

1. **tab 切回来 dt 会爆炸。** 你在后台待了 30 秒，切回来第一帧的「经过时间」是 30 秒。如果代码傻傻地把 30 秒喂给动画，粒子会瞬移。scroll.js 的做法是把每帧 dt 钳制在 0.1 秒以内（`Math.min(0.1, dt)`），超出就当作 0.1 秒——瞬间从后台回来也不会跳。

2. **后台冻结会让调试者误判。** 今天上午就是活例子：动画卡在半路，第一反应是「我改坏了」。判据其实很简单——把页面带到前台看它会不会自己恢复：会，就是 rAF 后台冻结；不会，才是真 bug。

3. **数帧必死，计时永生。** 任何动画进度都用时间戳算，别用「跑了第几帧」算。rAF 的帧率不保证稳定（后台、降频、高刷屏），只有时间是诚实的。

## 大白话术语表

| 术语 | 大白话 |
|------|--------|
| rAF | 浏览器提供的「下一帧画之前叫我」的函数，动画的心跳 |
| 帧（frame） | 屏幕画出的一张完整画面；60Hz 屏每秒 60 帧 |
| 帧率无关 | 动画速度按真实时间算，不按帧数算，任何屏幕速度一致 |
| lerp | 平滑插值：每帧向目标靠近一点，越近越慢，观感圆润 |
| tick | 一次心跳/一次帧回调；ticker 就是心跳器 |
| gsap.ticker | gsap 的心跳，一个 rAF 循环，驱动所有 gsap 动画 |
| lagSmoothing | gsap 的防跳机制：卡顿后假装只过了 33ms |
| dt / deltaTime | 两帧之间的实际经过时间（秒），所有动画推进的燃料 |
| 探针 | 调试时临时注入的一段代码，用来测量页面内部状态 |
| Page Visibility API | 浏览器提供的「页面在前台还是后台」检测接口 |
